# Reusery Vision

## Problem

Developers and coding agents repeatedly implement engineering problems that have already been solved elsewhere. Package registries, code search, dependency databases and vulnerability databases expose pieces of the answer, but they do not directly answer:

> Who has already solved this bounded engineering problem well enough that I should reuse it under these exact constraints?

## Thesis

Before an AI writes another version of a solved engineering problem, it should first know what humanity already knows.

Reusery resolves engineering intent against existing implementations, behavioural contracts, evidence, provenance and project policy.

The reusable unit is an engineering **primitive**, not necessarily a function or package. A concrete implementation of a primitive is a **specimen**.

## Intellectual lineage

Reusery explicitly draws inspiration from Joe Armstrong's work and writing on fine-grained software reuse, searchable metadata around reusable functions, and fitting software parts together. Reusery extends that direction into today's open-source ecosystem and AI-assisted engineering.

## Principles

1. Search before generating generic infrastructure.
2. Contracts matter more than names.
3. Evidence is multidimensional, not a universal score.
4. Provenance must be inspectable.
5. Absence of evidence is not evidence of quality.
6. BUILD LOCALLY is a valid successful resolution.
7. Prefer existing ecosystem indexes over rebuilding the world's code database.
8. Keep public engineering knowledge broadly accessible.
9. Never sell ranking or paid placement as trust.
10. Reusery itself should practise reuse.

## Commercial boundary

**Knowledge is free. Commercial assurance costs money.**

Public knowledge, ordinary resolution and open-source use should remain generous. Organisations can pay for private engineering memory, policy enforcement, continuous verification, private runners, compliance, scale and assurance.
